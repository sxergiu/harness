# 0.3.0

Three features and four fixes. The fix to read first is the one that was starting agents in
the wrong repository and then making itself more certain of it.

## A space that pinned itself to the wrong checkout, and then voted again

A space has no directory in Herdr, so the cockpit works one out from the panes it holds —
that inference is why starting an agent from a space needs no form. It was a plurality vote
re-counted on **every resync**, with no tie handling, so whichever cwd Herdr happened to list
first won a tie.

Measured on a live board: a space labelled `e-avize-site` held two agents in `repos/e-avize`,
and one agent plus one forgotten shell in `repos/claude-harness`. The vote came out 2–2,
listing order broke it for the wrong repo, and the header showed `repos/claude-harness`. Every
agent started from that space then launched **there** — and each new agent was another vote
for the wrong directory, so at 3–2 the mistake was settled for good. The vote reinforced its
own error, with nothing on screen saying so but a path in a header.

Three changes, and the third is what stops the feedback:

- **Agents outvote shells.** A bare shell is as often a window somebody opened elsewhere and
  forgot as it is the space's work, where an agent was started to do what the space exists
  for. Shells are read only when the space has no agent at all.
- **Our own instruments never vote** — the usage agent runs in `~/.harness`, which is nobody's
  repo, and an aside runs in its parent's cwd, a second voice for a directory that already has
  one.
- **A tie seeds nothing**, and the directory is seeded **once** and pinned from then on. A
  coin flip is not a wrong directory for one heartbeat but a wrong directory until somebody
  notices. A space with no clear answer simply has none, and starting an agent there asks you
  to type one — which that route already required.

Pinned by five tests, the first of which is the measured `e-avize-site` layout.

## A per-agent model switch, and the machine-wide default it would have moved

The agent header now carries a model picker — six aliases, five effort levels — and the
settings screen carries a cockpit-wide `--model` for agents the cockpit starts, stored in
`~/.harness/model`. **Out of the box no default is set and no flag is passed**, so an
untouched install starts agents exactly as 0.2.2 did.

The switch is sent as a typed `/model`, which is where the containment comes in. **Claude
Code's typed `/model` is not per-agent.** It sets the session *and* writes the alias to
`~/.claude/settings.json` as the default for every new session — read out of the v2.1.220
bundle, where both the typed `/model` and the typed `/effort` reach the user-settings writer
whenever the session is interactive, which a Herdr pane always is. The CLI separates the two
only inside its own picker, whose `for this session only` is a different key that a typed
command cannot press.

So a switch made for one agent was a switch made for the next agent anybody started, by hand
or from the cockpit, with nothing reporting it. The cockpit now records what the key said
before sending and puts it back once the CLI's write lands.

Three details, each of which fails invisibly:

- **The hold is keyed on the setting, never on the pane.** Two agents switched inside one
  window are two writes to one key, and the second must restore what the **first** one found.
- **It settles on the board's heartbeat and may not become a timer.** A `/model` at a busy
  agent queues behind the whole turn, so the write lands at a time nothing can predict;
  restoring after a fixed delay fires *before* it and leaves the file moved anyway — which on
  screen is indistinguishable from not having tried at all.
- **`max` takes no hold**, because the CLI writes nothing for it, and a hold would wait out
  its whole expiry for a write that never comes.

**What this does not close is the window itself**, and the picker says so where you press it.
Between the CLI's write and the restore the file really does hold the new alias — seconds at
an idle agent, the rest of the turn at a busy one — and an agent started by hand in those
seconds inherits it. A harness restarted inside the hold leaves the default moved, which is
what happened before any of this existed.

An alias is a request rather than an entitlement, and both the picker and the settings screen
say so: models are offered unfiltered because access belongs to the account and this cannot
enumerate it, so one you have no access to is refused in the pane, in the CLI's own words.

`~/.harness/effort` is **gone**, with the pinning that wrote it. That pinning defended the
cockpit's own starts by making a per-agent action write the global default, covered nothing
started by hand, and is the wrong shape once the leak is fixed at its source. There is no
`--effort` flag now: agents start at whatever your settings say, and the settings screen shows
that level read-only and names where it comes from.

## Answering the Claude in Chrome dialog, if you say it may

0.2.x made that dialog **visible** — without the detection rule `harness init` merges, an
agent sitting at one reads `idle` and the blocked panel never appears. This is the other half.
For someone who has already decided a browsing agent may browse, the panel appearing is the
whole cost: the agent stops until they come back to press a key they were always going to
press.

It is `~/.harness/chrome-autoaccept`, a checkbox in settings, **off** unless you turn it on,
and the file's existence is the entire setting. With it off the cockpit makes no extra request
and types nothing.

> **This is the only key this cockpit presses that nobody pressed.** Every other permission
> prompt — Bash, edits, anything else — still waits for you in the blocked panel, and turning
> this on says nothing about them.

**The digit is read off the screen, and it must never become a constant.** The
`Allow all actions on <host> for this session` row renders only where that offer stands, so
the list is `Allow / Deny` as often as it is `Allow / Allow-all / Deny` — and in the short
layout the `2` that means allow-for-the-session in the long one **is Deny**. A fixed keystroke
would refuse about as often as it allowed, and refuse invisibly: the agent carries on with a
no it was never given, which reads in the transcript and on the board exactly like yours.
Allow-all is preferred where it is offered, because it settles the host and stops the asking.

It reads the **live region only**, which is the same cut Herdr's own rule for this dialog
matches in. A pane read carries the scrollback with it, where a dialog answered minutes ago is
still sitting; by then the agent is blocked at something else, and that stale digit would
answer *that* prompt in your name. Every press is recorded in `~/.harness/harness.log`.

Ticking it with no detection rule installed is a setting that can never fire — the dialog
reads `idle`, so no agent is ever blocked at one and nothing calls this — and the settings
screen now says so rather than accepting the tick in silence. It is said, not prevented: the
box stays clickable, because turning it on before installing the rule is an order rather than
a mistake.

**Verified on the decline path only** — six real agent screens, the Herdr-blocked one among
them, all answered null. The allow path rests on the bundle read above and on the rule
measured against the real dialog. A dialog Claude Code restyles goes **quiet** rather than
wrong: the key is not found, and the blocked panel is still there for you.

## A context meter that granted 1M to sessions that never had it

The meter's usage is exact and its window has always been inferred, because a transcript says
`claude-opus-5` whether the session runs 200k or 1M. It was inferred from a machine-wide
claim — the `model` in `~/.claude/settings.json` — and `[1m]` there granted 1M to **every**
session.

On a machine whose settings say `opus[1m]`, a `sonnet` agent therefore reported its context as
a percentage of 1M: roughly five times too low, so a session close to full read as nearly
empty. The window now checks the **family**. The transcript cannot say `[1m]`, but it does say
`claude-sonnet-5`, which is enough to refuse.

The alias itself is now resolved by precedence rather than by taking the widest claim
available, which was the same bug one level up: the cockpit's own `--model` is true of agents
**it** started and says nothing about one started by hand, so applying it to every row handed
1M to agents that never carried the flag. It is recorded against the pane at the launch that
passed it, and the meter asks, in order, what the pane was switched to, what it was started
with, and only then what the machine default says. Each is a fact about something narrower
than the last, and every one of them still has to survive the family check.

Expect some meters to move. Anyone with `[1m]` in their settings running mixed-family agents
will see those agents jump to the honest, higher reading. That is the fix rather than a
regression, and refusing the wider window is the safe direction: it over-reports how full a
session is instead of hiding that one is nearly full.

## Each account keeps the last limits it had

Running two subscriptions meant switching blanked everything you knew about the other one:
the bars read the live account, so the account you just left had no numbers at all until you
went back to it. A reading is now hung on the account it was taken from, and a row that is
not live shows what it last had and how long ago — `session 12% · week 71% · 3h ago`.

The bars themselves are unchanged and still come from a live reading; nothing is ever drawn
from the cache for the account that is signed in. It is stored on the account row in
`~/.harness/accounts.json` rather than in a file of its own, because an account is `email`
**and** `orgId` and a second store keyed separately is a second place to key on the address
alone — which is the bug that once held the known list at a single row.

**There is no refresh on a cached row, and there cannot be.** These numbers are read by
driving `/usage` in an agent of ours, which only ever answers for the account that is signed
in, so refreshing another one would mean switching to it — and nothing here switches accounts
on its own. The `⇄ switch` you already have is the only way, and it is the human's.

**The reset time is not cached, and the type refuses it rather than a comment asking nicely.**
`Resets 3:20am (Europe/Bucharest)` is prose with no date in it, so a reading three days old
would render a reset that reads as upcoming and is long past, with nothing in the string able
to say otherwise. A percentage ages honestly beside a timestamp; a reset time does not age at
all.

## A login pane that outlived the harness

`claude auth login` runs in a visible pane, and which pane it is was held in memory — so a
harness restarted inside the few minutes that login is open forgot it. Under `npm run dev`,
where the server respawns on every save, that is ordinary rather than rare. The pane then
belonged to nobody: the cockpit could not finish it, and the next switch opened a second one
beside it.

It is now closed at the next switch, identified by its working directory rather than by a
name Herdr does not have for a shell — it is a bare shell in `~/.harness`, the one directory
that is ours, and the usage agent sharing that directory always carries an agent.

**Only at the next switch**, and deliberately not at startup or shutdown. A login may be
half-finished in a browser, where closing its pane takes the way back with it; that is why
shutdown already leaves it alone, and a sweep at startup would do exactly what shutdown is
careful not to. Asking for a new switch is the one signal that the old pane is spent. It is
still not *adopted* — `settle` decides on facts that did not survive the restart either, so
an adopted login could never be finished and would sit pending forever.

## Known, and not fixed here

- **The auto-accept warning is a warning.** Nothing stops you enabling a setting that cannot
  fire, and nothing enforces the dependency between the detection rule and the answer to it.
- **What the cockpit knows about a pane does not survive a restart.** The alias a pane was
  switched to, and the one it was started with, are in memory and dropped with the pane. After
  a restart the meter falls back to the machine default, and a session that outgrows it is
  recovered by the peak-widening rather than by the alias.
- **An override we did not write is not read.** Where the Herdr manifest carries somebody
  else's rules, the settings screen declines to claim whether this dialog is detected, because
  it cannot tell.
- Everything 0.2.x said about its own limits still holds. No cockpit has talked to a live
  Herdr off macOS, and every measurement quoted here was taken on one.
